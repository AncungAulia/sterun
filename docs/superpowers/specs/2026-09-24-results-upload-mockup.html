Recording a finish list (STE-58)

The last tab of the race console. An organiser uploads the timing system's CSV, reads what the backend found wrong with it, and records the rest on chain.

One fact shapes every screen: a result is permanent. `record_finish` moves a record to Finished and nothing can take it back, so the file is reviewed before anything is signed, and nothing the review flagged can be sent at all. That is not a nicety, it is the whole reason this screen has three steps instead of one button.

What changed today: the contract now records up to 120 results in one signature (STE-60, live since this morning). A 312-runner race used to mean 312 wallet prompts; it is now three.

The first two screens are not new. They are block 5 of 2026-09-13-org-console-mockup.html, which Ancung already approved: an empty tab holds the drop card and nothing else, and a loaded file is shaped like Entries, with the signing button in the header where every tab keeps its one action. What this file adds is what happens after that button: the held rows, the confirmation, the run, and the tab once results exist.

Screen 2. The button counts what will be published, never the rows in the file.

Two kinds of wrong, and only one is expensive

The chain would refuse it. An unknown bib, a runner who never checked in, a result already recorded. Cost: a failed transaction, nothing changes.

The chain would accept a lie. A bib two runners could claim, the same bib twice, an impossible time, a malformed row. Cost: a permanent false record. This is the kind the review exists for.

Held is held: there is deliberately no way to force one through from this screen. The way forward is a corrected file, which costs nothing.

The organiser never sees the backend's codes, only the sentence and what to do about it.

SCREEN 4

When a batch fails

The one screen that has to be right. Each batch is atomic, so a failure leaves the batches before it recorded and the ones after it untouched, and the screen has to say exactly that rather than "something went wrong".

Stopped after 120 results

120 results were recorded and are permanent. The remaining 188 were not sent, and nothing about them changed.

Your wallet did not answer on the second batch. Press Continue to send the rest; the runners already recorded are skipped, so nobody can be recorded twice.

  • Runners 241 to 308Not sent

Screen 4. Never "try again", which would read as repeating what already landed.

Why this wording, precisely

A batch that landed cannot be undone, so the screen must not suggest a retry undoes it. And a batch that was sent without an answer is not the same as one that failed: the console re-reads the records before continuing, and any runner already Finished is dropped from what remains.

This mirrors the scanner's rule from the race-day work: no answer is never read as sent, and the truth is settled by asking the chain, not by guessing from the error.
